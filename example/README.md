# recurrence_kit example

A single-screen demo app that exercises all three layers of the `recurrence_kit` package: the picker widget, the rule model, and the computation engine.

## Setup

From the example directory:

```bash
cd recurrence_kit/example
flutter pub get
flutter run
```

If the platform directories (`ios/`, `android/`, etc.) are missing after a fresh clone, regenerate them:

```bash
flutter create .
```

## What the app shows

The screen has four sections, all updating live as you interact with the picker:

**RecurrencePicker** — the full picker widget embedded in a card. Build any recurrence rule interactively: frequency, interval, weekday / day-of-month / weekday-position selection, the missing-day policy for days 29–31 and February 29, and end conditions.

**RecurrenceRule.displayText** — the human-readable summary generated by the rule model. Updates on every picker change to show what `displayText` produces for the current configuration.

**Next occurrences** — up to 5 dates computed by `RecurrenceEngine.nextOccurrences`, starting from today. If today is an occurrence it appears as the first entry. Below the list, a summary line derived from `RecurrenceEngine.lastOccurrence` reads "Ends <date>." for a schedule that ends, "Never ends." for an unbounded one, or "No occurrences." when the schedule has none.

**RecurrenceRule.toJson()** — the rule's JSON serialization, pretty-printed and selectable. Useful as a reference for consumers planning persistence.

## Theme toggle

The sun/moon icon in the app bar switches between two `RecurrencePickerTheme` configurations: a default light theme and a dark theme with a green accent. The picker card background also swaps to demonstrate how theming works in practice.

## Key implementation patterns

The example demonstrates several patterns that consumers of the package will likely need:

**The rule and the start date are the whole schedule.** Every engine call takes both and nothing else. An "ends after N" rule needs no resolution step: `nextOccurrences` and `lastOccurrence` interpret the count directly. See `_recompute`.

**Keeping computation out of `build`.** Occurrence computation is cached in state fields (`_upcoming`, `_lastOccurrence`, `_jsonString`) and recomputed only when the rule changes, not on every frame rebuild. This avoids lag when rapidly tapping stepper controls.

**Inclusive queries.** `nextOccurrences` is inclusive of the date it is given, so the example passes the start date itself and today's occurrence, if any, is included.

**Distinguishing "never ends" from "no occurrences".** `lastOccurrence` is null for both an unbounded schedule and an empty one. The example resolves the ambiguity from state it already has: an empty `_upcoming` (queried from the start date) means the schedule has no occurrences; a non-empty one with no last occurrence is unbounded. See `_endSummary`.

**A controlled picker.** The picker holds no recurrence state of its own; `onChanged` hands the app a complete replacement rule and the app stores it with `setState`. Whatever the app stores is what the picker shows.
